# Engineering Principles
## The Foreman
### Version 1.0

---

# Introduction

Software is more than code.

Every design decision influences how people think, work, and solve problems.

These principles exist to ensure that every contribution—whether written by a human developer or an AI assistant—moves The Foreman closer to its mission.

When uncertainty exists, these principles take precedence over convenience.

---

# Principle 1
## Build the Foundation First

### Philosophy

Strong systems are built upon stable foundations.

Features built on weak architecture eventually become technical debt.

The Foreman should always prioritize reliability before expansion.

### In Practice

- Build core functionality before advanced features.
- Prefer maintainable code over clever code.
- Avoid shortcuts that compromise long-term stability.
- Every version should remain deployable.

### Example

Good:

> Build the Capacity Engine before adding AI recommendations.

Poor:

> Add impressive features before the underlying system is dependable.

---

# Principle 2
## Bring Clarity to Complexity

### Philosophy

Complexity belongs inside the software.

Clarity belongs in the user experience.

The Foreman should simplify difficult decisions instead of exposing unnecessary information.

### In Practice

- Reduce visual clutter.
- Use plain language.
- Hide implementation details.
- Present only what is useful now.

### Every screen should answer a question.

If a screen exists without helping the user make a decision, reconsider its purpose.

---

# Principle 3
## Give Confidence Through Clarity

### Philosophy

Recommendations without explanation create uncertainty.

The Foreman should explain why it recommends something whenever practical.

### In Practice

Instead of saying:

> Buy plywood.

Explain:

> Existing inventory is below the minimum required for the next scheduled project.

Users should understand the reasoning.

Trust is earned through transparency.

---

# Principle 4
## Keep the Work Moving

### Philosophy

Perfection is not the objective.

Progress is.

The Foreman should encourage steady, meaningful progress rather than overwhelming users with impossible expectations.

### In Practice

- Recommend the next logical task.
- Reduce decision fatigue.
- Break large goals into achievable steps.
- Celebrate completion.

---

# Principle 5
## Protect Capacity

### Philosophy

Time.

Energy.

Money.

Materials.

Attention.

All are limited resources.

The Foreman should never assume unlimited capacity.

### In Practice

Recommendations should consider:

- Available time
- Work schedule
- Commute
- Inventory
- Budget
- Current workload
- Energy level (when available)

The best plan is the one that realistically fits today's capacity.

---

# Principle 6
## Consistency Beats Heroics

### Philosophy

Long-term success comes from repeated small improvements.

The Foreman should encourage sustainable habits rather than unrealistic bursts of productivity.

### In Practice

Avoid encouraging:

- Overcommitment
- Excessive multitasking
- Unrealistic schedules

Favor:

- Daily progress
- Healthy pacing
- Continuous improvement

---

# Principle 7
## Build for Utility Before Opportunity

### Philosophy

The Foreman was created to solve real problems.

Commercial opportunity must never become more important than usefulness.

Every feature should first answer:

> Does this genuinely help the person using it?

If the answer is no...

It does not belong.

### In Practice

Before implementing a feature ask:

- Does this solve a real problem?
- Will it reduce cognitive load?
- Will it improve decision making?
- Will it actually be used?

If not...

Do not build it.

---

# Principle 8
## The Instrument

### Philosophy

The Foreman is an instrument.

It is not the craftsman.

Its purpose is not to replace human judgment.

Its purpose is to strengthen it.

The user remains responsible for every important decision.

The Foreman simply helps them make better ones.

### In Practice

The Foreman should:

- organize information
- recognize patterns
- recommend actions
- explain reasoning
- reduce mental load

The Foreman should never remove ownership from its user.

---

# Engineering Standards

Every contribution should strive to be:

- Modular
- Readable
- Maintainable
- Documented
- Testable
- Explainable

Future developers should understand code without needing its original author.

---

# Green Build Standard

Every development session ends with a Green Build.

A Green Build means:

- The application launches.
- Existing functionality works.
- No known critical errors exist.
- Documentation remains current.

No feature is complete until it reaches Green Build status.

---

# AI Contributors

Artificial Intelligence is a development tool.

Not an authority.

AI contributors should:

- Read the Constitution.
- Read the Founder's Letter.
- Follow these Engineering Principles.
- Preserve simplicity.
- Preserve architecture.
- Avoid unnecessary complexity.

AI may assist.

The Founder decides.

---

# Final Thought

Technology will continue to evolve.

Programming languages will change.

Frameworks will change.

Artificial intelligence will improve.

These principles should remain recognizable regardless of how The Foreman is implemented.

Every line of code should answer one question:

> Does this help someone become the best version of themselves?

If the answer is yes...

Keep the work moving.
